四、已核实的真实缺口与改进项（6 项）

G1 · ⚠️ 向量长期记忆无可观测 / 清理接口 api/modules.py:647-698 · core/memory
/memory/* 仅覆盖 MEMORY.md / USER.md / SOUL.md 文件型记忆。向量长期记忆（MemoryManager / VectorMemoryProvider）只能经 /settings 整体开关重建，无按用户查看 / 检索 / 清空的 API。
影响：开启向量记忆后，管理员无法审计「某用户沉淀了多少向量记忆」或按需清理，属于可观测性缺口。
建议：新增 GET /api/v1/memory/vector（统计/列举）+ DELETE /api/v1/memory/vector（按 owner 清空），或纳入 /admin/status 展示向量记忆体量。
G2 · ⚠️ 无主动登出 / 令牌吊销端点 api/auth.py（后端源码无 logout/revoke）
鉴权为无状态 Bearer，token 仅在改密 bump_epoch 时失效，服务端无任何 logout / revoke / 强制下线接口。
影响：多用户/审计场景下，用户无法主动使当前会话失效；管理员无法强制下线某账号（只能改其密码连带踢掉所有人）。
建议：新增 POST /api/v1/auth/logout（将当前 jti/token 加入吊销表，AuthService.verify 回查）或 POST /api/v1/users/:uid/revoke（admin 强制抬高 epoch）。
G3 · 🔸 /me 与 /change-password 绕过 require_auth 的 X-Act-As 分支 api/auth.py:76-110
两端点用内联 _current() 而非全站统一的 require_auth(perm) 依赖，因此不经过 admin 的 X-Act-As 代管逻辑。
影响：行为正确（身份初始化不应被代管穿透；改密有专用 admin 端点 /users/:uid/password），但与全站守卫范式不一致，增加维护认知成本。
建议：统一走 require_auth 并显式 skip_act_as=True，消除特例。
G4 · 🔸 前端 authStatus() 包装函数无调用方（死代码） frontend/src/api/auth.ts:7
authStatus() 导出但全仓无任何调用；后端 GET /api/v1/auth/status 端点存在且仅在登录页「判断鉴权是否开启/用户数」时有用，但前端登录页直接尝试 login，未消费该端点。
影响：轻微——端点可用但未利用，登录页无法据此优化「是否展示密码框 / 是否提示初始化」。非死端点，仅是前端包装冗余。
建议：登录页改为先调 auth/status 判断部署形态（匿名/密码登录/已建用户），或删除该未用包装。
G5 · ✅ 模型选择持久化 —— 初查误报，已核实为无缺口 frontend/src/stores/app.ts:12/85/100/101
初查曾标记「模型选择刷新后重置」为半闭环。经核验：app.selectedModel 已持久化到 localStorage('zhishu.selectedModel')，刷新保留；对话发送时回填 model: app.selectedModel。非服务端 per-user，但自托管单部署完全可接受。结论：无缺口，特此澄清以免误导。
G6 · ⚠️ 脱敏无独立管理闭环（按设计为自测接口） api/admin.py:34 · core/redact.py
POST /admin/redact 仅为自测接口；脱敏实际作用在审计日志落库。无「查看脱敏规则 / 预览全部已脱敏字段 / 脱敏命中统计」的管理端点（开关在 /settings）。
影响：合规审计人员无法量化「系统已脱敏多少条敏感数据」。
建议：在系统页增加「脱敏命中统计」（可在 /admin/status 或新增 /admin/redact/stats 返回计数），闭环可观测。
