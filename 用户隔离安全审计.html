智枢 zhishu-agent · 用户间数据隔离审计报告

审计时间：2026-07-29 ｜ 范围：后端鉴权、数据存储、REST 路由、Agent 工具层、文件/媒体、RBAC ｜ 提交基准：9ba6fc0
总体结论： REST 路由层（HTTP API）的隔离基本正确，但对话实际调用的「Agent 工具层」存在多处严重跨用户泄漏。 根因是：系统以字符串 username 作为隔离维度（无 tenant 概念），而工具层在调用 RAG / 会话记忆 / 长期记忆 / 文件系统时普遍不传递 owner 上下文。 默认智能体的工具集就包含 knowledge_search / session_search / memory / read_file，因此任意登录用户都能在聊天中触发这些泄漏。

一、已正确隔离的部分（正面发现）

  • 对话 CRUD 全部按 owner 校验（core/conversations.py:71-113）。
  • 知识库 REST 接口（list/get/delete/search/reparse）均按 owner 过滤（api/knowledge.py）。
  • 聊天启动的自动 RAG 上下文按 owner 构建（system_prompt.py:75）。
  • Agent 自身对话历史按 owner:session 前缀隔离（api/chat.py:202 + memory 存储）。
  • RBAC 矩阵实现正确（admin=*、operator、user、viewer 权限收口于 require_auth(perm)）。
  • Provider API Key 在 REST 响应中已掩码（credentials.py:89,94-100）。
  • 外部向量长期记忆（opt-in）按 owner 过滤（memory/backends.py:64-72）。

二、严重问题（需立即修复）

#严重度问题 / 位置说明
1严重 知识库检索跨用户
core/tools/builtins/knowledge.py:17		 knowledge_search 调用 ctx.kb.query(q, top_k) 未传 owner。VectorStore.search 在 owner=None 时返回全体用户私有向量（core/vector_store.py:165-170）。模型一旦调用该工具，即可检索并引用其他用户私有知识库内容。
2严重 会话记忆全局可读
core/tools/builtins/sessions.py:33-92		 session_search 直接查询全局 turns 表，完全无视 ctx.user。三种模式均可越权：① 无参浏览所有用户的会话列表；② 关键词跨所有用户对话全文检索；③ 传他人 session_id 翻阅其完整对话。这是对话隔离最严重缺口。
3严重 长期记忆全局共享
core/tools/builtins/memory.py:32-33		 记忆读写落在 data_dir/MEMORY.md|USER.md|SOUL.md 单一全局文件，无 owner 维度。任意用户 recall 看到他人沉淀，update_user 可覆盖他人画像；且自动反思 maybe_reflect 写入后，经 build_agent_context_prompt 注入每个用户每轮的系统提示——A 的对话事实会出现在 B 的提示词里。
4严重 read_file 越权读整个后端
core/tools/builtins/file.py:52-66		 _resolve_read_path 把允许范围放宽到 work_root = os.path.dirname(data_dir)，即 backend 整个工作区。任意用户可读 providers.json（含加密密钥，配合默认 secret 可解密）、其它用户附件、后端源码。
5严重 chat/parse 任意文件读取
api/chat.py:133-166		 /chat/parse 接收 path 参数，当非 /media/ 前缀时直接 abs_path = p 当作绝对路径读取并解析，再把原文回显在响应中、且入库到当前用户 KB。攻击者可借此读取服务器任意文件（如 providers.json、他人附件）并让模型复述。
6严重 知识库 doc_id 同名碰撞
core/rag.py:927 + core/vector_store.py:91-117		 doc_id 默认取文件名。用户 A 上传 报告.pdf 后，用户 B 也上传同名文件：documents 表 UPSERT 把 owner 改为 B，而 vectors 表是纯 INSERT——A 的分块向量仍留在同一 doc_id 下。B 以 owner=B 检索时命中该 doc_id，会把 A 的私有内容一并返回（越权读他人内容）。
7严重 /media 静态挂载无鉴权
main.py:78-81		 app.mount("/media", StaticFiles(...)) 无任何鉴权。任何人拿到 /media/... URL（结合 #4 可枚举他人附件路径）即可直接下载其他用户的附件、生成图/视频、PDF 渲染图。
8严重 默认签名密钥可伪造 token
core/config.py:233		 默认 secret = "change-me-zhishu-secret"，启动仅告警不阻断。token 的 u(用户) 与 r(角色) 均签名于此密钥，攻击者可离线伪造 {"u":"victim","r":"admin"} 的 token，直接冒充任意用户 / 提权为 admin。

三、高风险 / 中风险

#严重度问题 / 位置说明
9高危 普通用户可读 MCP/插件密钥
api/modules.py:67,256-262		 user 角色拥有 modules:read，而 list_mcp 返回 item["env"]（常含第三方 API Key），get_plugin 直接返回完整 info（含 env）。任意登录用户可读到这些密钥。
10高危 enable_auth=False 隔离全失效
api/auth.py:52-53,94-95		 关闭鉴权时所有请求等价于 admin，且数据归属同一 "anonymous"。多人共用即全部对话/知识库混在一起。该开关默认 True 但为全局项，需在部署文档中强制告警。
11中 cron 任务列表不过滤 owner
core/cron.py:218-229 + api/cron.py:38		 list_jobs() 返回全部任务、不过滤 owner。operator 可看到其他 operator/admin 创建的定时任务及其 payload（可能含敏感提示词）。属权限过宽。
12设计 owner=NULL 表示全局共享文档
core/vector_store.py:11-12,165-170		 知识库 owner 为 NULL 的文档对全体用户可见/可检索（设计意图）。但上传时若 owner 被误置 NULL（见 #6），文档即变为全局可见，需在产品与审计中明确标注此语义。

四、修复优先级与建议

P0 — Agent 工具层隔离（核心，对应 #1~#6）

  • knowledge_search：改为 ctx.kb.query(q, top_k, owner=ctx.user)；并让 ToolContext 始终携带 user。
  • session_search：所有查询追加 WHERE session LIKE '{owner}:%' 过滤；无参浏览也限定当前用户会话。
  • memory 工具：记忆文件改为按 owner 分目录（如 data_dir/memory/{owner}/MEMORY.md），或改用 opt-in 的向量长期记忆（已按 owner 隔离）；自动反思注入也按 owner 隔离。
  • read_file / file_read：把允许根目录收紧到用户沙箱（如 data_dir/users/{owner}/），不再包含 backend 父目录。
  • chat/parse：仅接受本会话已落盘的 stored_path//media/ 相对路径，禁止绝对路径，并校验路径归属当前用户。
  • 知识库 doc_id：改用服务端生成的随机 UUID（uuid.uuid4().hex），避免文件名碰撞导致的向量混合。

P1 — 基础设施加固（#7~#10）

  • /media：改为带 token 鉴权的路由，或按用户目录 + 不可枚举 token 命名；附件归属用户目录。
  • secret：部署若仍为默认值，启动直接阻断（而非仅告警），强制要求随机密钥。
  • modules:read：对 user 角色脱敏 env 字段（仅 admin/operator 可见）。
  • enable_auth=False：在文档与启动日志中强制标注「单用户专用、禁止多用户」。.
  • cron list：按 owner 过滤（或仅返回自己的任务）。

验证方式

  • 用两个普通用户 alice / bob 分别建对话、传私有文档、写记忆；
  • 以 bob 身份在聊天中调用 session_search / knowledge_search / memory，断言无法看到 alice 的内容；
  • 尝试 read_file("/app/backend/zhishu/data/providers.json") 与 /chat/parse?path=/etc/passwd，断言被拒绝；
  • 伪造 {"u":"admin","r":"admin"} token，断言 401（修复 #8 后）。
